# 000-P-001-RC

**ID:** 000-P-001-RC

**Category:** Core Requirement

**Title:** Core Requirement Glossary

## Description
Defines the essential, unique, referencable terms for the project, enabling a concise and dense glossary that supports traceability, testability, and consistent usage across all requirements and acceptance criteria.

## Acceptance Criteria

### AC-001.1: Term Uniqueness
- Every term appears only once across the project documentation.
- No duplicate terms are allowed in any requirement or acceptance criterion.

### AC-001.2: Concise Definition
- Each term has a concise, unambiguous definition present in the glossary.
- Definitions use simple, specific language without vague qualifiers.

### AC-001.3: Traceability
- Every term is traceable back to a project, goal, phase, stakeholder need, or higher‑level requirement.
- Links are explicit and verifiable.

### AC-001.4: Testability
- Each term should have an associated check or test that can verify correct usage.
- Testability is assessed through the Dense Referencable Checklist.

### AC-001.5: Convention Consistency
- Terms follow the project's abbreviation and naming conventions 
- Deviations must be documented and justified.
- glossary filename convention right now like `RC‑` : ###-<phase>-###-glos
where first ### is related to the phase 

### AC-001.6: Glossary reuse
- Glossaries can be connected to a bigger set. Works via "connected:" <glossary_list>

## Dense Referencable Checklist

Before accepting any requirement or term, verify:

1. **Unique** – the term appears nowhere else in the project glossary.
2. **Defined** – a concise, unambiguous definition is present.
3. **Traceable** – the term links back to a goal, phase, or higher‑level requirement.
4. **Testable** – there exists a test or check that can confirm the term’s correct usage.
5. **Consistent** – the term follows the abbreviation and naming conventions (e.g., `RC‑`, `AC‑` prefixes).
